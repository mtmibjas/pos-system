# Security Rules

Scope: authentication, authorization, transport, signing, secret handling. Tenant isolation lives in `docs/tenant-rules.md`.

## Auth model

### JWT (access token)

- Algorithm: **EdDSA (Ed25519)** or **RS256**. **Never `HS256`** with a shared secret — too easy to misuse.
- Lifetime: **15 minutes**. Short on purpose.
- Required claims:
  - `iss` — issuer (cloud-api)
  - `sub` — user_id (UUID)
  - `aud` — audience (`pos-platform`)
  - `tenant_id` — UUID, see `docs/tenant-rules.md`
  - `role` — `cashier` / `manager` / `owner` / `admin`
  - `device_id` — registered device fingerprint
  - `jti` — unique token id (for revocation)
  - `iat`, `exp`, `nbf`

- Tokens are signed by `cloud-api` only. Local-store-server and POS clients **verify** but never **issue**.
- Key rotation: signing key id (`kid`) is in the JWS header. Clients fetch JWKS from `cloud-api` with caching. Old keys stay verifiable for one rotation window.

### Refresh tokens

- **Rotation on every use** (the old refresh token is invalidated when a new one is issued).
- Stored hashed at the cloud (never plaintext).
- Bound to `device_id`. Stealing a refresh token without the device is useless because the server checks device fingerprint at refresh time.
- Lifetime: **30 days**, sliding (each use resets the clock up to a hard 90-day max).

### Device registration

- Every device (POS install, mobile install) registers once and gets a `device_id` + an Ed25519 device keypair (private key stored in OS keychain / Android Keystore / iOS Keychain — never in plain files).
- Registration requires a one-time enrollment code generated by an `owner` or `admin` for that tenant.
- A revoked device cannot refresh or sign operations.

## Signed operations

> The sync transport is encrypted (TLS), but operations themselves are also **signed**.

- Every `Operation` is wrapped in a `pos.v1.SignedEnvelope` whose signature is computed over the inner payload bytes with the device's Ed25519 key.
- The cloud verifies the signature against the device's registered public key before accepting.
- This defends against:
  - Replay attacks (combined with `operation_id` dedupe + a sliding nonce window)
  - Compromised transport (defence in depth on top of TLS)
  - Insider tampering at intermediaries

## Transport

- **TLS 1.3 only** between local-store-server and cloud-api.
- Cloud-api enforces HSTS for browser-facing endpoints.
- Internal POS ↔ local-store-server LAN traffic: TLS recommended; if the deployment is single-host (`localhost:8080`), plain HTTP is acceptable because the loopback interface is the trust boundary.

## Secrets

- **No secrets in source control.** Enforced by a pre-commit hook (later phase).
- Cloud: **AWS Secrets Manager** (chosen — see `infra/terraform/README.md`). Secrets are read by `cloud-api` at startup; rotation is automatic for DB credentials and manual-with-alarm for signing keys.
- Local-store-server: OS keychain for the device key; an `.env` file (gitignored) for non-key config in dev only.
- Rotate JWT signing keys every 90 days; refresh-token hashing pepper every 180 days.

## Authorization (RBAC)

Roles:

| Role     | Can |
|----------|-----|
| `cashier` | Create sales, take payments, issue refunds (capped amount), look up products |
| `manager` | Cashier + void invoices, large refunds, run stock takes, manage cashiers |
| `owner`   | Manager + view reports, manage stores, register devices |
| `admin`   | Owner + tenant config, billing (cloud-api only; never present at store) |

Permissions are checked in every handler — never trusted from the client UI. Tests cover "lower role attempts higher action" rejection.

## Audit

Every security-sensitive action emits an event:
- `user_logged_in`, `user_logged_out`, `login_failed`
- `device_registered`, `device_revoked`
- `permission_denied`
- `key_rotated`
- `refund_completed` (financial sensitivity)

Audit events go to the same operations_log + are mirrored to a write-once observability sink at the cloud.

## Threats explicitly out of scope (defer)

These are real but Phase 5+:
- Hardware tamper evidence on POS terminals
- PCI-DSS for card data (we will not store PANs; we use tokenized gateway responses)
- Penetration testing program
- Bug bounty

## Tests required

- Unit: JWT validation (alg confusion, expired, wrong audience, missing claims).
- Integration: refresh-token rotation invalidates the old one; revoked device cannot sync; signed-envelope tampering detected.
- Security review: dedicated review before Phase 3 (when sync goes to cloud).
